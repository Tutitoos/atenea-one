# L2 v1: tramas Ethernet sobre DATA y configuración firmada v3 (borrador)

- **Estado:** **Propuesto** (2026-10-26). **No normativo** hasta que el responsable acepte [ADR-010](../architecture/ADR-010-l2-ethernet.md). No describe nada implementado ni verificado; los valores numéricos marcados «hipótesis» son a medir.
- **Relacionados:** [wire-v2](wire-v2.md) (DATA sin cambios), [relay-v2](relay-v2.md), [signed-config-v1](signed-config-v1.md) y [signed-config-v2](signed-config-v2.md) (el cuerpo v3 los extiende), [MTU](mtu.md), modelo de amenazas T31–T45 propuestas en ADR-010 §7.
- Convenciones de [signed-config-v1 §1](signed-config-v1.md): enteros big-endian, `vec<T>` con contador, listas ordenadas ascendentes por su codificación y sin duplicados, codificación única, `flags` reservados = 0 (`Malformed`). «Debe»/«no debe» son requisitos del borrador.

## 0. Alcance y límites honestos

L2 v1 es un **modo Ethernet de dispositivo**, no un puente de aprendizaje: cada dispositivo es un nodo con una MAC firmada; el agente **responde localmente** ARP y ND con la tabla firmada; solo cruzan el cable tramas IPv4/IPv6 unicast a la MAC de un par y, opcionalmente, mDNS. Quedan **fuera** de v1: puente a LAN física, 802.1Q, DHCP, RA, STP/LLDP, fragmentación, jumbo, otros EtherTypes, macOS/Windows (ADR-010 §1, D1).

## 1. Cutover y compatibilidad

1. **Wire-v2 y relay-v2 no cambian.** Una trama Ethernet es el payload de un DATA `type=3` (wire-v2 §1). Sin byte de tipo interno, sin cabecera propia, sin cambio de handshake, contadores, antirreplay, cookies ni rekey.
2. **Modo por red, firmado.** El cuerpo de `DeviceConfig` pasa a admitir `version = 3` **solo para redes L2**. El emisor emite `1`/`2` (bytes idénticos a hoy) para redes L3 y `3` únicamente para redes L2; un cuerpo v3 es siempre L2 (§2, `net_mode = 1`). Un cuerpo v3 sin ningún campo L2 propio no existe: `net_mode` es obligatorio.
3. Un agente que solo entienda 1/2 devuelve `UnsupportedVersion` ante v3 (**falla cerrado**, T42). Un agente que entienda v3 pero no pueda crear TAP (macOS/Windows en v1, o Linux sin `/dev/net/tun`) **rechaza aplicar** la configuración con el error local `UnsupportedL2Mode` (no es un error de verificación y no modifica el estado; la configuración sigue siendo válida). Nunca degrada a L3.
4. `IssuerCert`, `DeviceBundle`, `SignedConfig` (`magic`, `version = 1`), dominios de firma y pasos 1–13 de verificación **no cambian**. Un cuerpo v3 se firma con el dominio `"atenea-one/config/v1"` igual que v1/v2 (la versión va dentro del cuerpo firmado).
5. **El modo es inmutable por red:** un emisor no cambia una red L3 a L2 ni al revés; se crea una red nueva con otro `network_id`. El agente que ya persistió `net_mode` de un `network_id` rechaza una configuración con otro modo (`ScopeMismatch`).

## 2. Cuerpo de configuración v3

Cuerpo v3 = campos de v2 con las siguientes diferencias.

**Peer v3:** `device_id [16]`, `noise_pubkey [32]`, `flags u8 = 0`, `addrs vec<Addr>(u8) 1..4`, `endpoints vec<Endpoint>(u8) 0..4`, **`routes` = vacío** (debe valer 0; el campo existe para conservar el esquema de v2), y tras `routes`:

| Campo | Tipo | Regla |
| --- | --- | --- |
| `mac` | `[6]` | MAC de ese par (ver «Regla de MAC») |
| `extra_macs` | `vec<[6]>(u8)` 0..8 | MAC adicionales que ese par puede usar como origen (p. ej. interfaces secundarias del propio dispositivo); misma regla; ordenadas, sin duplicados |
| `max_learned` | u8 | 0..16; en v1 **debe ser 0** (aprendizaje diferido, véase §6); el campo se reserva para v3-b |

**Cuerpo v3**, tras `dns_domains`:

| Campo | Tipo | Regla |
| --- | --- | --- |
| `net_mode` | u8 | `1` = L2. Otro valor: `Malformed` |
| `mac` | `[6]` | MAC de **este** dispositivo |
| `extra_macs` | `vec<[6]>(u8)` 0..8 | como en el par |
| `flood` | u8 | `0` = `proxy` (sin difusión/multicast); `1` = `mdns` (replicación acotada de mDNS, §10). Otro valor: `Malformed` |
| `flood_pps`, `flood_burst` | u16, u16 | si `flood = 0`, deben ser 0; si `flood = 1`, `1 ≤ flood_pps ≤ 200` y `flood_pps ≤ flood_burst ≤ 400` (hipótesis, §12) |
| `l2_rules` | `vec<L2Rule>(u16)` 0..128 | ordenadas por su codificación, sin duplicados |

`mtu` conserva su campo y rango (1280..1500) con un **significado nuevo en v3: longitud máxima de trama Ethernet** (§4). `advertised` debe estar **vacío**; `routes` de cada par, vacío (`InvalidStructure`).

**L2Rule** (solo permisos; denegación por defecto):

| Campo | Tipo |
| --- | --- |
| `src` | `L2Selector` |
| `dst` | `L2Selector` |
| `ethertype` | u16: `0` = cualquiera de los permitidos (§5); `0x0800`, `0x0806`, `0x86DD` |
| `vlan` | u16: **debe valer 0** en v1 (sin etiqueta); reservado para 802.1Q |

**L2Selector:** `kind u8` — `1` cualquiera (sin datos), `2` dispositivo (`device_id [16]`: él mismo o un par; coincide con su `mac` y `extra_macs`), `3` MAC (`[6]` exacta), `4` OUI (`[3]`: primeros tres bytes), `5` multicast de grupo (cualquier MAC con el bit de grupo, incluida la difusión; sin datos).

**Regla de MAC.** Toda MAC (`mac` y `extra_macs`, propia y de pares) debe ser unicast (bit 0 del primer byte = 0) y administrada localmente (bit 1 = 1): `b0 & 0x03 == 0x02`. Todas las MAC de la configuración (propias, de pares y extra) son **únicas**. La MAC de un dispositivo es un campo firmado; su asignación es del control plane. Generación recomendada (no verificada por el agente, que solo comprueba la regla y la unicidad):

```
mac = 0x02 || BLAKE2s-256("atenea-one/l2-mac/v1" || network_id[16] || device_id[16])[0..5]
```

Si colisiona, el emisor añade un byte de contador `ctr = 1, 2, …` al final de la entrada y reintenta. Ejemplo calculado con `hashlib.blake2s` de Python el 2026-10-26 (**una sola implementación; falta contraste independiente**, mismo criterio que wire-v2 §7): `network_id = 07`×16, `device_id = 01`×16 → digest `e597faa43eee5ded2a8f83a8cbf383ae4ee71c532b983b7eb19ece0594d5372b` → MAC `02:e5:97:fa:a4:3e`; con `device_id = 02`×16 → `02:ca:a0:5f:7c:a4`.

### Reglas estructurales adicionales (paso 14, `InvalidStructure`)

1. Reglas de MAC anteriores. 2. `advertised` vacío y `routes` de pares vacías. 3. Selectores `device` de `l2_rules` referencian al dispositivo o a un par. 4. `extra_macs` ordenadas/únicas (`Malformed` si no). 5. Las direcciones, prefijos y reglas L3 de v1/v2 se verifican como hasta ahora (la ACL L3 sigue aplicándose, §7). 6. `dns_*` según v2.

### Vectores exigidos

Uno válido v3 y un negativo por regla en `tests/fixtures/identity/`; v1 y v2 válidos de fases 3 y 7 siguen aceptándose byte a byte; v3 con `net_mode` inválido; MAC multicast, universal o duplicada; `max_learned ≠ 0`; `flood` inválido; `routes`/`advertised` no vacías; fuzz del parser v3.

## 3. Plano de datos: orden de validación

### 3.1 Recepción (trama de un par, tras AEAD y antirreplay de wire-v2)

Descarte silencioso con contador en el primer fallo, en este orden:

1. Payload no vacío (vacío = keepalive, sin cambio).
2. Longitud `14 ≤ len ≤ mtu` (§4). Sin FCS ni relleno obligatorio.
3. EtherType (bytes 12..14) en `{0x0800, 0x0806, 0x86DD}`. Valores ≤ 0x05DC (longitud 802.3), `0x8100`/`0x88A8` (VLAN), `0x88CC` (LLDP), o cualquier otro: descarte. Destinos de STP (`01:80:C2:00:00:00`) descartados antes por no ser un EtherType permitido.
4. **MAC origen** (bytes 6..12) = `mac` o alguna `extra_macs` **del par que autenticó Noise para esa sesión**. Cualquier otra: `rx_src_mac_mismatch`.
5. **MAC destino** (bytes 0..6): la `mac` propia, o una MAC de grupo permitida por §10 (`flood = 1`). Unicast a otra MAC (incluidas MAC de otros pares): descarte; **nunca se reenvía** (sin tránsito).
6. EtherType `0x0806` (ARP) y paquetes ICMPv6 de ND (tipos 133–137), así como RA y DHCP: **descartados** en v1 (`rx_l2ctl_dropped`). ARP/ND son siempre locales (§7).
7. IPv4/IPv6: validar con `classify` de `crates/policies` (longitud IP declarada ≤ resto de la trama; el resto se ignora como relleno Ethernet sin entregarse más allá de la longitud IP), **IP origen ∈ `addrs` del par** (los `routes` están vacíos en L2) y destino = dirección propia (o grupo permitido, §10). Si no, descarte.
8. ACL L2 (§8), y después ACL L3 sobre el flujo IP (`Policy::allows`); **ambas** deben permitir.
9. Entregar al TAP. Si la cola del TAP está llena: descartar la nueva (`rx_queue_full`).

### 3.2 Emisión (trama leída del TAP)

1. Longitud `14 ≤ len ≤ mtu`; EtherType permitido; si no, descarte (`tx_ethertype_dropped`, `tx_oversize`).
2. **MAC origen** = `mac` propia o `extra_macs` propias (si el host la cambió, `tx_src_mac_mismatch`).
3. ARP/ND: §7 (respuesta local, nunca viajan). RA, DHCP (UDP 67/68): descartados.
4. MAC destino unicast: buscar en la tabla (§6): par con esa MAC, **o descartar** (`tx_unknown_dst`; sin inundación de unicast desconocido). Validar IP origen ∈ `tunnel_addrs` propias y destino ∈ `addrs` del par; ACL L2 y L3 en origen.
5. MAC destino de grupo: solo si `flood = 1` y es mDNS (§10); si no, descarte (`tx_flood_dropped`).
6. Cifrar/enviar como DATA al par (P2P o relay por el motor existente). Cola por par acotada; si se llena, descartar el nuevo.

## 4. MTU y tamaños

- `mtu` (campo de la configuración) es la **longitud máxima de trama Ethernet** = payload máximo del DATA. El datagrama en el cable mide `30 + len(trama)` ≤ 1530 (wire-v2 §1); relay-v2 admite DATA E2E ≤ 1530, por lo que el relay no cambia.
- **MTU IP de la interfaz TAP = `mtu − 14`** (1386 con el valor por defecto 1400; 1486 como máximo). Sin 802.1Q no hay −4. El agente fija esa MTU en `configure_link`.
- Con el valor por defecto (1400) el datagrama P2P ocupa `1400+30+8+20 = 1458` sobre IPv4 y `1478` sobre IPv6 (mtu.md). Un host que pretenda MTU IP 1500 (trama 1514) **no cabe** sin fragmentar el UDP externo: no se fragmenta ni se reensambla nada en v1; el administrador debe bajar la MTU de los hosts o aceptar que se pierda lo mayor.
- El fallback TLS/TCP de relay añade su propia sobrecarga (mtu.md): se recalculará al medir.
- Trama mayor que `mtu`, incluidas las jumbo: descarte con `tx_oversize`/`rx_oversize`.
- Mínimo: 14 (cabecera). Tramas Ethernet «cortas» (< 60) se aceptan; el TAP no exige relleno.

## 5. Tipos de trama y comportamiento ante inválidos

| EtherType | v1 | Notas |
| --- | --- | --- |
| `0x0800` IPv4 | Sí | Unicast al par; mDNS si `flood = 1` |
| `0x86DD` IPv6 | Sí | Unicast al par; mDNS si `flood = 1`; ND local (§7) |
| `0x0806` ARP | Solo local | Respondido por el agente; **no cruza el cable** |
| `0x8100`, `0x88A8` | No | VLAN, diferido (D6) |
| `0x88CC`, STP/LLC, EAPOL, MRP, cualquier otro | No | Descarte contado |

Una trama inválida (longitud, EtherType, MAC, cabecera IP/ARP incoherente) se descarta **sin respuesta al par** y sin cerrar la sesión. Contadores locales, sin payload ni MAC completas en los registros (solo recuento y motivo; opcionalmente MAC truncada a OUI).

## 6. Tabla de MAC

- **Estática:** construida al aplicar la configuración: `mac` y `extra_macs` de cada par → par. Sin envejecimiento; se reconstruye atómicamente al cambiar la configuración. Tamaño ≤ `256 × 9` entradas (peers ≤ 256 por v1) acotado por construcción.
- **Aprendida:** **no existe en v1** (`max_learned = 0`). Está reservada para el modo puente (D3-B). Si en el futuro se habilita: ≤ `max_learned` (≤ 16) por par, ≤ 4096 por red y dispositivo, envejecimiento de 300 s sin tráfico, barrido cada 5 s, primer propietario gana, sin movimiento entre pares mientras la entrada viva, `mac_conflict` por intento; la MAC origen aprendida solo puede ser unicast administrada localmente y nunca igual a una MAC estática de otro par.
- Una colisión de MAC entre redes es irrelevante: cada red tiene su tabla (§11).
- Contadores: `l2_table_entries`, `l2_table_rejected`.

## 7. ARP y Neighbor Discovery locales

Sin cambios en el wire. El agente observa el TAP y **construye la respuesta localmente**:

- **ARP request** (`oper = 1`, `htype = 1`, `ptype = 0x0800`, `hlen = 6`, `plen = 4`) con `tpa` ∈ `addrs` IPv4 de un par: responder con ARP reply (`sha` = MAC firmada del par, `spa` = `tpa`, `tha`/`tpa` del solicitante) escrita en el TAP; `sha` del request = MAC origen de la trama y `spa` ∈ `tunnel_addrs` propias, o se ignora. `tpa` no perteneciente a ningún par: **sin respuesta y sin enviar nada**. Probes (`spa = 0.0.0.0`) y ARP gratuitos propios: ignorados.
- **Neighbor Solicitation** (ICMPv6 135) con target ∈ `addrs` IPv6 de un par: responder con Neighbor Advertisement (flags solicited/override, opción TLLA = MAC del par) al origen. NS de DAD (origen `::`): ignorar (la unicidad de dirección la garantiza la configuración firmada). RS (133), RA (134), Redirect (137), NA entrantes del TAP: descartados en v1.
- Respuestas locales ≤ `l2_ctl_pps` por clase (hipótesis, §12); excedentes se descartan (`l2ctl_ratelimited`).
- Efecto: ni ARP ni ND se transportan; un par hostil **no puede** envenenar la caché del host vecino porque las tramas ARP/ND recibidas se descartan (§3.1.6) (T32). La vigencia de las respuestas es la de la configuración firmada vigente.

## 8. ACL L2 e integración con `crates/policies`

- **Denegación por defecto.** Una trama se permite en origen y en destino solo si alguna `L2Rule` coincide: `src`/`dst` por selector, `ethertype` (0 = cualquiera de los tres permitidos), `vlan = 0`. Selectores: ver §2. Sin reglas L2 ⇒ **ninguna** trama pasa.
- **Orden:** L2 antes que L3. Una trama IP pasa la ACL L2 y, después, `Policy::allows` (reglas L3 de v1/v2) sobre su flujo. Las reglas L3 no cambian de formato ni de significado.
- **API propuesta** (prosa; no es código): `crates/policies` ganaría una evaluación `allows_l2` sobre una descripción de trama `(MAC origen, MAC destino, EtherType)` con la misma semántica «solo permisos» y el mismo recorrido por un conjunto ordenado de reglas; los selectores `device` se resuelven contra `mac`/`extra_macs` del dispositivo o par igual que `Policy::new` resuelve `addrs`. El motor llamaría `allows_l2` y después `allows` en cada trama IP (recepción y emisión).
- **Regla inversa:** como en F6/T1, una ACL L2 permisiva en un sentido autoriza respuestas en el otro solo si hay regla; no se infiere nada.

## 9. Aislamiento entre redes

Una red L2 = un `network_id` = un TAP = una tabla = unos cubos de tasa = un conjunto de sesiones. El prólogo Noise (`atenea-one/v2 || network_id`) ya separa redes. El agente no comparte ningún estado L2 entre redes de un mismo proceso (en v1 hay una red por instancia, véase ADR-010 §2.4); si en el futuro hubiera varias, cada una tiene su propio TAP y sus propias estructuras, sin tabla ni caché común, y una MAC repetida entre redes no tiene efecto.

## 10. Difusión y multicast (`flood`)

- **`flood = 0` (por defecto de la propuesta, D5-A):** toda trama con MAC de grupo (incluida difusión) leída del TAP o recibida de un par se descarta. ARP/ND ya son locales; no hay nada que replicar.
- **`flood = 1` (`mdns`, opt-in por red):** solo se replica una trama IPv4 con destino MAC `01:00:5e:00:00:fb`/IP `224.0.0.251` o IPv6 con MAC `33:33:00:00:00:fb`/IP `ff02::fb`, protocolo UDP, puerto destino 5353, TTL/Hop Limit 255, origen en `tunnel_addrs`. Cualquier otra trama de grupo: descarte.
  - **Emisión:** una copia por par autorizado por la ACL L2 (selector `kind 5` en `dst`) y por la ACL L3 del flujo, cada una como DATA ordinario con su contador; presupuesto compartido `flood_pps` / `flood_burst` por dispositivo y copias totales por segundo ≤ `flood_pps × peers` (se descartan las que excedan, `flood_ratelimited`). Cola de réplicas por par acotada.
  - **Recepción:** se acepta del par si cumple 3.1 con destino mDNS y ACL; cubo por par de ingreso (`flood_pps`, `flood_burst`); **nunca se reenvía** a otros pares.
  - **Sin reflexión** mDNS a otras redes o a la LAN física. **No** hay DHCP: UDP 67/68 descartado siempre.
- Otra difusión/multicast (SSDP, LLMNR, NetBIOS, difusión dirigida, RA) queda fuera de v1.

## 11. Prevención de bucles

1. **Estructural:** el overlay es una malla sin tránsito: nada recibido de un par se reenvía a otro (§3.1.5) y no hay STP ni tabla de reenvío entre pares. Un bucle solo puede cerrarse **fuera** del agente.
2. **Puente local:** al arrancar y cada 5 s el agente comprueba si el TAP tiene un dispositivo maestro (puente/bond) y lo informa (`bridged`); en v1 el valor por defecto es **rechazar emitir difusión** y registrar alarma (política final: D3). *(La existencia de `/sys/class/net/<if>/master` es conocimiento general de Linux, **sin comprobar en este entorno**.)*
3. **Eco:** una réplica inyectada en el TAP desde un par se anota por hash de 64 bits con clave aleatoria por proceso (ventana de 256 entradas/2 s); si la misma trama vuelve a leerse del TAP se descarta (`loop_suspected`). Al superar 10 detecciones en 1 s se **suspende la difusión** 30 s (`loop_quarantine`) y se alarma.
4. Sin TTL propio en tramas Ethernet; no se añade uno en v1.

## 12. Límites de tasa y presupuestos (hipótesis a medir)

| Recurso | Valor propuesto | Efecto al superar |
| --- | --- | --- |
| Respuestas ARP/ND locales | 200/s y ráfaga 400 por dispositivo (`l2_ctl_pps`, local) | descarte, `l2ctl_ratelimited` |
| mDNS emitido | `flood_pps`/`flood_burst` firmados (1..200/400) | descarte, `flood_ratelimited` |
| Ingreso mDNS por par | igual que lo firmado | descarte, `rx_flood_ratelimited` |
| Unicast por par | ≤ cuota del relay (2000 pps, 24 Mbit/s, relay-v2 §5) como techo externo; techo local `l2_pps` por par **sin valor** hasta medir | descarte del nuevo |
| Tabla | ≤ 256×9 (estática) | n/a |
| Cola TAP→motor / motor→TAP | acotadas (tamaño a medir); descartar el nuevo | `tx_queue_full`, `rx_queue_full` |

Estos parámetros no cambian formatos ni autentican; son defensa operativa, no garantía de disponibilidad (mismo criterio que wire-v2 §8).

## 13. Contadores IPC propuestos

Estables y locales (como wire-v2 §5): `rx_src_mac_mismatch`, `rx_unknown_ethertype`, `rx_oversize`, `rx_l2ctl_dropped`, `rx_acl_l2_denied`, `rx_queue_full`, `tx_src_mac_mismatch`, `tx_unknown_dst`, `tx_oversize`, `tx_ethertype_dropped`, `tx_flood_dropped`, `tx_queue_full`, `l2ctl_ratelimited`, `flood_ratelimited`, `rx_flood_ratelimited`, `loop_suspected`, `loop_quarantine`, `l2_table_entries`, `bridged`. Sin identificadores de par ni direcciones completas en logs.

## 14. Pruebas obligatorias para aceptar la especificación

Formato de trama: mínimos/máximos exactos (13, 14, `mtu`, `mtu+1`), cada EtherType permitido/denegado, 802.3 length, 0x8100, jumbo; MAC origen de otro par y de ninguno; destino unicast ajeno (0 reenvío); ARP/ND forjados descartados; respuesta local correcta; solicitudes de direcciones desconocidas sin tráfico; tabla constante bajo inundación de MAC nuevas; mDNS acotado y no reenviado; eco detectado; puente detectado; dos redes aisladas con MAC repetida; v1/v2/v3 mezclados (v3 rechazado por parsers antiguos, v1/v2 intactos); `UnsupportedL2Mode` sin cambiar estado; fuzz del parser de tramas y del cuerpo v3; propiedad `round_trip`. Laboratorio y orden en [fase-10-plan](../operations/fase-10-plan.md).

## 15. Riesgos y decisiones abiertas

- Decisiones D1–D7 de ADR-010 §9 condicionan este borrador (SO, VLAN, puente, `flood`).
- `l2_pps`, tamaños de cola y tasas son **hipótesis**; `mtu` 1400 con tap de 1386 puede sorprender a administradores acostumbrados a 1500.
- El modo de dispositivo no sirve para LAN/VMs detrás de un dispositivo (se usan subredes L3, ADR-007) y no ofrece las funciones de un conmutador de aprendizaje; no debe anunciarse como equivalente de otros productos.
- La derivación de MAC de 40 bits tiene riesgo de colisión muy bajo pero no nulo; el emisor lo trata con `ctr`.
- Sin implementación ni vectores: ningún comportamiento de este documento está verificado.
